# 검협전 — 검토 결과와 수정 제안

문서 버전 1.0 · 2026-10-08 · HTML: `../html/review-fix-plan.html`

## 1. 범위와 상태

사용자 요청은 검토 내용을 읽기 쉬운 HTML과 개발 인계용 MD에 정리하는 것이다. 이번 작업은 문서 작성이며 게임 코드·씬·밸런스를 변경하지 않는다. 이전 검토 이후에도 사운드 호출 등이 추가되고 있어 아래 근거는 문서 작성 시 읽은 파일 기준이다. 실제 수정 직전 다시 읽고 최신 작업을 보존해야 한다.

근거: BattleFlow, PlayerDash, Health, EnemyProjectile, StatEffects, CombatResolver, SelectionWheelView, ExchangeDirector 및 구현 현황 문서. 저장된 s8-3 미리보기와 기존 빌드 로그를 검토했다. 이번 문서 작성 중 Unity 컴파일·Play 테스트를 새로 실행하지 않았다.

구분:
- **코드에서 확인:** 현재 구현의 데이터 흐름 또는 처리 방식.
- **위험/가설:** 그 구현에서 예상되는 플레이 문제. Play 재현은 별도 필요.
- **수정 제안:** 아직 적용하거나 사용자 승인받지 않은 변경안.
- **기능 확장:** 초기 목표를 완성하는 작업으로, 기존 동작의 버그 수정과 구분.

## 3. R1 — 일시정지 중 시간이 서로 다르게 흐름

### 확인한 사실

- `Battle/PlayerDash.cs`의 Update는 매 프레임 `cooldown.Tick(Time.unscaledDeltaTime)`를 먼저 실행한다. 메뉴 중에도 대쉬 충전이 진행된다.
- `Battle/Health.cs`는 무적 종료를 `Time.unscaledTime` 절대 시각으로 계산한다. 메뉴를 켜고 기다리는 동안에도 무적 시간이 만료된다.
- `Battle/BattleFlow.cs`는 paused이면 Update에서 반환하므로 그 안의 패링·특수기 쿨타임은 멈춘다.
- EnemyMayAct에는 paused 조건이 없다. 적 이동은 Time.deltaTime=0으로 멈추지만 투사체 등 일부 시스템은 정지 상태에서도 판정 코드를 실행할 여지가 있다.

### 예상 문제

대쉬 후 메뉴에서 기다리면 대쉬는 재충전되고 다른 기술은 충전되지 않는다. 회피 도중 메뉴를 열면 이동은 정지한 채 무적만 끝날 수 있다. 이것은 확정된 코드 흐름이며 직접 플레이 재현은 아직 하지 않았다.

### 내가 수정한다면

1. **제안 정책:** 메뉴에서는 전투 시간을 모두 정지한다. 선택 타이머와 교환 연출은 기존 실제 시간 감각을 유지하되 메뉴 정지와 슬로모션을 구분한다.
2. `BattleClock` 같은 작은 시간 제공자를 두는 안을 제안한다. `CombatRealDelta = paused ? 0 : unscaledDeltaTime`, `WorldDelta = paused ? 0 : deltaTime`. 메뉴 UI는 자체 실제 시간을 사용할 수 있다. 모든 시스템을 전역 Manager에 합치지 않는다.
3. Health의 절대 시각 `invulnerableUntil`을 남은 시간으로 바꾸거나, 메뉴 동안 멈추는 전투 시각을 사용한다. 호출부가 정해진 한 곳에서 Tick하도록 하여 이중 감소를 막는다.
4. PlayerDash 쿨타임·패링 시간·비도 회복·특수기·기록의 시간 기준을 점검한다. 전투 기록의 메뉴 시간 포함 여부는 별도 결정한다.
5. EnemyMayAct가 paused일 때 false가 되도록 하여 멈춰 있는 투사체의 피격·엄폐 처리도 정지한다.

Time.timeScale=0만 검사해서 모든 시간을 멈추는 방식은 피한다. 선택과 히트스톱은 메뉴와 다른 규칙일 수 있으므로 원인을 명시해야 한다. 슬로모션에서 대쉬 무적이 줄어드는 기준은 기존 실제 시간 사양과 연결하여 확인한다.

### 검증

- 대쉬 직후 메뉴 3초 대기 → 재개 시 남은 충전·무적 시간이 메뉴 전과 동일.
- 패링·베기·마무리·비도 회복도 동일한 메뉴 정책을 따른다.
- 메뉴 중 HP·투사체 위치와 피격 상태가 변하지 않는다.
- 선택 전체 제한시간 1/1.3/1.5/2초와 기존 히트스톱은 유지된다.
- 재시작·타이틀 이동 시 정지 상태와 무적 상태가 남지 않는다.

## 4. R2 — 투사체가 높이를 무시함

### 확인한 사실

- `Enemy/EnemyProjectile.cs`는 투사체를 이동시킨 다음 플레이어와의 차이를 수평면에 투영하고, `radius + 0.35`로 피격 여부를 판단한다.
- 따라서 플레이어가 위로 점프해도 같은 수평 위치면 높이와 무관하게 피격될 수 있다.
- 이전 위치와 현재 위치 사이의 경로가 아니라 이동 후 한 지점만 검사한다. 빠른 투사체 또는 낮은 프레임에서 몸체·엄폐를 통과할 위험도 있다.

### 내가 수정한다면

1. 플레이어의 실제 CharacterController 몸체를 피격 캡슐로 사용한다. 단순히 두 Transform의 3D 거리만 비교하면 발 위치 기준 때문에 다른 오차가 생기므로 캡슐을 사용한다.
2. 투사체 이전 위치→예정 위치 구간을 반지름 포함해 검사한다. 몸체에는 선분-캡슐 거리 검사 또는 적절한 Physics sweep, 엄폐에는 SphereCast/겹침 검사를 제안한다.
3. 몸체와 엄폐가 같은 프레임에 걸리면 경로상 먼저 닿은 대상부터 처리한다. 시작점이 이미 겹친 경우도 별도 검사한다.
4. 피격이 성립한 뒤에는 기존 `EnemyBrain.ReportHit → Health.TakeDamage` 경로를 사용한다. 패링·대쉬 무적을 새로 중복 구현하지 않는다.
5. 선택·교환·일시정지 중 투사체 정지 정책을 유지하고, 공격 종료·씬 종료 시 잔존 투사체를 정리한다.

점프했다고 항상 회피 성공시키지는 않는다. 점프 중에도 실제 몸 캡슐이 투사체 궤적에 겹치면 맞는 것이 제안 기준이다. 몸체 크기·투사체 반지름과 보이는 모형의 오차도 확인해야 한다.

### 검증

- 지상 몸통 관통 → 피격 1회.
- 점프 중 몸 캡슐 아래로 통과 → 피격 없음.
- 점프 중 몸 캡슐에 닿음 → 기존 무적·패링 규칙에 따라 처리.
- 낮은 FPS에서 한 프레임에 몸체를 넘어 이동해도 경로상 피격 검출.
- 몸체보다 앞에 엄폐 존재 → 엄폐가 먼저 막음. 뒤에 있는 엄폐가 앞선 몸체 피격을 취소하지 않음.
- 선택·일시정지 중 투사체가 멈추고 정지 중 피해가 발생하지 않음.

## 5. R3 — 현재 상태와 변경 이력 구분

### 확인한 사실

`md/implementation-status.md`에 과거의 '적은 정지', '공격·적 AI·점프·회피 등 아직 미구현'이 현재처럼 남아 있고, 다음 작업에 이미 구현한 S3·S4가 등장한다. 같은 파일 뒤쪽에는 S8-3 UI·S8-2 캐릭터·적 AI 완료 기록이 있다. 실제 코드에는 예전 PrototypeHUD가 없어 목록도 최신화가 필요하다.

### 내가 수정한다면

- 상단에 **현재 실행 방법·실제 작성 모듈·검증 상태·남은 작업**만 둔다.
- 기존 기록은 지우지 않고 '날짜별 변경 이력' 아래로 이동하며 과거 상태임을 표시한다.
- roadmap의 단계 ID를 진행 기준으로 삼고 다른 문서는 그 상태를 참조한다. 서로 다른 P/S 번호를 최신 단계처럼 섞지 않는다.
- 각 항목은 '코드 작성 / 컴파일 확인 / 규칙 검사 / Play 재현 / 사용자 체감 확인'으로 나눈다. 기존 로그의 날짜와 검사 대상을 기록한다.
- 최신 사운드 등 병행 작업을 다시 읽고 포함한다. 다른 담당자 수정분을 덮어쓰지 않는다.

완료 기준: 처음 읽는 담당자가 Title 씬 시작 방법과 실제 남은 작업을 알 수 있고, 현재 코드와 문서의 모듈 목록이 일치한다. 모든 기존 변경 기록은 보존한다.

## 6. R4 — 선택 휠이 검을 가림

### 확인한 사실

`UI/SelectionWheelView.cs`는 중심 부근 `(0.5, 0.52)`에 560×560 기준 휠을 배치한다. 비선택 칸의 어두운 배경도 높은 불투명도(0.9)를 사용한다. 저장된 `html/s8-3-battle.png`에서는 플레이어와 검이 휠 아래에 크게 겹친다. 게임 전체 해상도에서 동일한지는 Play 확인이 필요하다.

### 내가 수정한다면

**우선 제안:** 휠을 화면 오른쪽으로 옮기고 플레이어·검은 중앙 왼쪽에 보이게 한다. 예약 슬롯과 타이머는 휠 가까이 둔다. 입력은 기존 가상 커서의 논리 좌표를 유지하고 표시 위치만 바꿔 혼동을 줄인다.

대안은 중앙 배치를 유지하되 크기와 배경 불투명도를 낮추는 것이다. 다만 작은 글씨로 성공률 읽기가 어려워질 수 있어 시안 비교가 필요하다. 선택 완료 후에는 기존처럼 휠을 숨기고 연출을 본다.

먼저 HTML 와이어프레임으로 위치를 확인받고, Unity UI 변경 후 1920×1080·1280×720·16:10 등에서 폰트·타이머·슬롯이 잘리지 않는지 검사한다. 특정 크기와 알파값은 시안 승인 뒤 정한다. 현재 반응 속도와 8방향 입력 의미를 변경하지 않는다.

## 7. R5 — 검 위치·적 스탯 판정 확장

### 확인한 사실

현재 StrikeContext에는 정면/후면·동일 방향 반복·좌우 패널티·비도 패널티·공중 보정이 있다. 성공률 계산은 플레이어 스탯을 받으며, 검 시작자세와 적 검 자세·적 스탯을 직접 입력받지 않는다. 검 끝자세는 연출과 UI의 회전 베기 표시에는 사용된다.

따라서 '검 자세 때문에 어떤 공격이 유리한가'라는 초기 게임 목표는 아직 판정에 충분히 연결되지 않았다. 이는 버그라기보다 핵심 기능 확장이다. 앞선 담당자가 만든 현재 수식을 틀렸다고 단정하지 않는다.

### 내가 수정한다면

1. 양측 스탯·위치·방향·검 자세를 가진 `CombatSnapshot`을 도입하는 안을 제안한다. 시각 모델에서 판정 수치를 직접 읽기보다 규칙용 검 자세 데이터를 둔다.
2. 방향 비교 기준(캐릭터/상대/화면 좌표)을 먼저 확정한다. 카메라가 돌았다고 같은 검 궤적의 의미가 바뀌지 않도록 변환 경계를 둔다.
3. '시작 검 자세 × 공격 목표 방향 × 적 방어 자세'에서 유리/중립/불리 관계표를 먼저 만들고 사용자에게 그림으로 확인받는다. 임의 상성이나 수치를 생성하지 않는다.
4. CombatEvaluator가 예상 성공률과 피해를 만들고 HUD와 Resolver가 같은 경로를 쓴다. 규칙은 연출과 분리한다.
5. 예약 평가 시 상태를 고정할지, 선행 공격 뒤 검 자세를 예측해 적용할지 결정한다. 실패/패링 후 다음 검 자세가 달라진다면 UI의 후속타 수치도 그 조건을 명확히 설명한다.
6. 기존 반복 둘째 타 보정·좌우 기억·치명타·확정 성공 기술을 유지할지 명시하고 결합 순서·확률 상하한을 정한다.

확정 성공인 반격·베기·마무리가 신규 수식 때문에 실패하지 않도록 현재 확정 규칙을 확인한다. 현재 테스트 수치가 최종 밸런스라는 의미는 아니다.

### 필요한 사용자 결정

- 내 검 시작 위치와 적 검 방어 위치가 어떤 관계일 때 유리한가?
- 적은 어떤 스탯을 가지며 성공률과 피해에 어떻게 영향을 주는가?
- 후속타는 선택 시점의 스냅샷으로 고정하는가, 앞 타 결과에 따라 달라지는가?
- 방어와 패링을 독립 결과/확률로 나누는가?

검증: 같은 입력·고정 난수에서 결과 재현, 같은 Snapshot의 UI/실제 수치 일치, 좌표 변환 검증, 반복 보정 중복 적용 없음, 확정 성공 예외 보존. 게임 체감은 실제 정면·후면·검 자세 조합 플레이로 확인한다.

## 8. 실제 수정 순서 제안

1. **문서 현행화:** R3으로 현재 코드·승인 기록·검증 로그를 맞춘다.
2. **시간과 투사체:** R1/R2를 작은 변경으로 처리하고 Play 재현으로 검증한다.
3. **시야:** R4 시안 선택 후 UI만 조정하고 방향 입력·예약 규칙 회귀 확인.
4. **검술 규칙:** R5의 관계표·수식을 확인받고 별도 구현한다.
5. Title → 스탯 → 입구 → 단타/콤보 → 패링/회피/점프 → 승패/재시작까지 한 판을 반복 검증한다.

이번 완료 상태: 검토 문서와 HTML 그림 작성. 코드 수정·새 컴파일·새 Play 검증 미실시. 다음 작업자는 먼저 최신 파일과 추가 사용자 답변을 읽고 이 제안서를 구현 완료 기록으로 오해하지 않는다.

## 9. Claude 의견 · 해결법 3안 · 순위 (2026-10-08)

코드를 다시 읽고 지적을 모두 대조했다. R1~R5 모두 사실이다(R2는 투사체 높이 1.3m라 점프로 피할 수 있는 높이가 아니어서 체감은 작지만, 빠른 이동 시 통과 위험은 실제). R5는 버그가 아니라 게임 규칙 결정이 필요한 확장이다. 사용자 "그걸로 해결해보자"(2026-10-08)에 따라 R1~R4는 1순위 안으로 구현하고, R5는 규칙 결정이 필요하므로 안만 제시한다.
